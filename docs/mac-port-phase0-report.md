# MultiCapture macOS対応 Phase 0 検証報告

- 実施日：2026-10-05
- 環境：Mac mini（M4、メモリ 24GB）、macOS 27.0.1、Google Chrome 156、FFmpeg 9.0.2、Python 3.14.8（Homebrew）、Swift 6.4
- ディスプレイ：外部 4K を 2 枚（どちらも等倍。Retina の確認は、1 枚を HiDPI に切り替えて行った）
- 検証コード：`tools/mac-spike/`（使い方は同ディレクトリの README.md）。生の結果は `tools/mac-spike/results/`（git 管理外）

## 1. 結論

S1 の「完全に隠れたウィンドウ」だけが不合格だった。原因は macOS 側にあり、Chrome のフラグでは直せない。ただし、ウィンドウが 10px でも見えていれば 30fps 近くで取り込めるので、代案②（重ならない配置）より緩い「一部が見えている配置」で要件を満たせる。それ以外の項目は、未実施の部分を除いて合格した。

**Phase 1 に進んでよいと判断する。** Phase 1（共通化と同時録画数の自動決定）は、Phase 0 の未実施項目に依存しない。

## 3. 採用するフラグと手法

**Chrome**

- 既存の `RENDER_FLAGS` をそのまま使う。`--force-device-scale-factor=1` は Retina 対策として必須。
- `--disable-features=MacWebContentsOcclusion` は効果がなかったので、追加しない。
- キーチェーンは既定のまま使う（mock は使わない）。ダイアログが出るという報告があれば、全インスタンスに mock を付ける。

**映像（ScreenCaptureKit）**

- `SCContentFilter(desktopIndependentWindow:)`、`420v`（NV12）、`captureResolution = .nominal`、`colorMatrix` は 709。
- 補助プログラムは CLI でも `NSApplication.shared` を初期化する。しないと SCStream の開始時に `CGS_REQUIRE_INIT` で落ちる。
- 録画用ウィンドウは、どれも一部が画面に見えている状態を保つ。既定はカスケード配置（36px ずつずらす）とする。

**音声（Core Audio タップ）**

- 対象は、ブラウザ本体の子孫のうち `--utility-sub-type=audio.mojom.AudioService` を持つプロセス。補助プログラムに本体の PID を渡し、子孫の中からオーディオのプロセスオブジェクトを持つものを選ばせる方式で、正しく選ばれた。
- 予備策として `--disable-features=AudioServiceOutOfProcess` と本体の PID の組み合わせも使える。

**時刻**

- 映像の PTS と、音声の `mHostTime` から求めた秒は、同じ時間軸に乗る。
- Python 3.14 では `perf_counter` も mach_absolute_time と一致していた（差 0.006ms）。それでも、要件どおり mac の `Clock` は ctypes で mach_absolute_time を読む実装にする。

## 4. 設計に反映すること（Phase 2 以降）

1. **隠れたウィンドウの間引き**：録画用ウィンドウが完全に隠れると、コマが 4fps 前後まで落ちる。設定画面とログで注意を促し、実行中に fps が落ちたら警告する。録画中は MultiCapture 自身のウィンドウも、録画用ウィンドウを完全には覆わない位置に置く。
2. **ロックと画面オフ**：コマが止まる。caffeinate でのスリープ防止に加え、README に「ロックしない」と書く。補助プログラムの stall イベントで検出してログに残す。
3. **音声のサンプルレート**：集約デバイスは、主デバイス（既定の出力）のレートで動く。FIIO K13 R2R では 192kHz だった。補助プログラムで 48kHz に変換する（AVAudioConverter）。出力デバイスを切り替えるとレートも変わるので、作り直しの処理と合わせて扱う。
4. **画面操作による乱れ**：測定中にスクリーンショットなどの操作をすると、映像に 0.3〜0.8 秒の空白が出て、音ズレが −14〜+52ms の範囲で段差状に変わった。既存のフォールバック（ずれが大きいときの補正）とログが、mac でも必要になる。
5. **取り込みの間隔**：上限を 30fps にすると、30fps の動画に対して平均 29.3fps になり、まれに 1 コマ取りこぼす。上限を 60fps にすると取りこぼしはなくなるが、同じコマが重複して届く（平均 40fps）。どちらにするかは Phase 2 のつなぎ目の検証で決める。
6. **色**：暗いグレー（元動画で RGB 31）が、取り込むと 26 になる。白は一致した。SCK の色空間の指定を含めて、Phase 2 で詰める。
7. **画面より大きいウィンドウ**：Chrome は高さだけを画面に収め（4096x2700 を指定すると 4096x2498 になる）、幅ははみ出したまま開く。はみ出した部分も SCK で取り込める。
8. **権限の主体**：アプリから起動した補助プログラムは、アプリの許可を引き継ぐ（S8②）。ソースから起動した場合は、起動元の端末の許可で判定される。SSH 経由だと `sshd-keygen-wrapper` になり、画面収録は必ず拒否される。検証では、補助プログラムが自分自身を責任プロセスとして起動し直す方式（`responsibility_spawnattrs_setdisclaim`）で回避した。ソースから起動するときもこの方式を使うかは、Phase 2 で決める。
9. **配布**：
   - Gatekeeper の手順（macOS 27）は、一度開こうとする →「プライバシーとセキュリティ」の「このまま開く」→ 確認ダイアログで「このまま開く」。
   - 隔離されたアプリは App Translocation で別の場所から起動される。補助プログラムは、バンドル内の相対パスで探す。
   - アップデートのたびに許可の付け直しが要ることを README に書く。
10. **ビルド環境**：Homebrew の Python 3.14 には tkinter がない。ビルドには `python-tk` が要る。PyInstaller 6.22.3 は Python 3.14 で動いた。
