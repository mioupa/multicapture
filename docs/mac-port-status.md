## 2. 要件定義書と違う点

| 項目 | 要件定義書 | 実装 | 理由 |
|---|---|---|---|
| ソースから起動したときの許可 | Terminal に許可を与える | 補助プログラム（MultiCapture Capture）に許可を与える。補助プログラムは責任プロセスを自分に切り替えて起動し直す（`--disclaim`） | SSH 経由や、音声録音の説明文を持たない端末（Ghostty など）では、端末に許可を与えても音声タップが使えない。.app から起動したときは従来どおりアプリの許可を引き継ぐ |
| 隠れたウィンドウ | 重なっていても録画できるようにする | 各ウィンドウの一部が見えている必要がある | 完全に隠れたウィンドウは、macOS が ScreenCaptureKit への受け渡しを 4fps 前後まで間引く（Chrome 以外のアプリでも同じ）。10px 見えていれば 30fps 出る |
| M4 の上限 | 7本（付録 A） | 6本（1080p・30fps） | §5.6 の式（計測値 × 0.85）どおり。ユーザー確認済み |
| 録画前の待機 | なし | mac は区間録画の開始前に 30 秒待つ | 起動直後は Chrome とmacOS の処理が重なり、コマ落ちが約10倍になる |
| 音声のサンプルレート | 48kHz で取得 | 集約デバイスは出力機器のレートで動く（例：192kHz）。補助プログラムで 48kHz に変換する | Phase 0 で判明 |
| 音声のタイムスタンプ | mHostTime | mHostTime ＋出力機器の遅延 | タップの音は鳴る前のもの。Chrome は鳴る時刻に映像を合わせるため |
| SCK のコマ | complete のコマを使う | 直前と画素がまったく同じコマは捨てる | SCK は中身の変わらないコマも渡す。区間録画は届いたコマを順に書くので、WGC と同じ「変わったときだけ」にそろえた |
| VideoToolbox の画質 | 実装時に決める | `-q:v 55`（x264 の CRF 23 と同等の SSIM、ビットレート 1.2〜1.3倍） | `tools/verify/vt_quality.py` |
| FFmpeg の同梱 | arm64 の静的ビルド、GPL | 公式ソースから外部ライブラリなしでビルドした LGPL の静的ビルド | 第三者のバイナリに頼らずに済む。x264 は含まない（VideoToolbox を使う） |
| バージョン | — | 2.0.0 | ユーザー決定 |
| バンドル ID | — | `io.github.satoa-may5.multicapture` | ユーザー決定（今後変えない） |

## 3. Windows に影響する変更

Phase 1 のリファクタ（動作は変えない）に加えて、次の変更が Windows にも効く。

- `find_join`（区間のつなぎ目の照合）の 1 コマずれを修正した。「最良の一致と同じくらい」の許容幅を、比較範囲の最大と最小の差ではなく、最良の一致を基準にした。範囲内にフラッシュや場面転換があると、隣のコマが候補に入って 1 コマ欠けることがあった。シーク位置もコマの中間に置くようにした
- 上限の計測に失敗しても、録画は止めずに従来の上限 8 で続ける。計測の詳細は `data/logs/capacity.log` に残す
- 予約録画（無人）のときは、警告などのダイアログを出さずに情報欄へ表示する（自動停止が止まらないように）
- `build.ps1`：Scoop の shim の ffmpeg.exe を同梱してしまう不具合を直した

## 4. 検証結果（Mac mini M4、macOS 27.0.1、Chrome 156）

テスト動画（`tools/verify/make_test_video.py`）を `tools/verify/check_recording.py` で検査した。

| 条件 | 結果 |
|---|---|
| 5分・2本・1920x1080 | 欠け 0、重複 0、音ズレ 中央値 −10ms・幅 19ms |
| 5分・6本・1920x1080（画面共有なし、待機 30 秒） | つなぎ目 5か所はすべて正常。途中の乱れは欠け2・重複2。最初の区間の先頭 1.5 秒に欠けと重複が十数件。音ズレは先頭を除いて 40ms 以内 |
| 2ページ・2分（ページを同時録画） | 2ファイルとも保存。録画側の取りこぼし 0。音ズレ 40ms 以内 |
| CPU 使用率（6本録画中） | 平均 65% 前後（目安の 50% を超える） |

## 5. 既知の課題

1. **最初の区間の先頭 1.5 秒**：負荷が高いと、再生開始直後のコマが乱れる（録画全体の先頭だけ）
2. **CPU 使用率**：6本で 65% 前後。Python の録画ループのスレッドのカーネル時間が大きい（6本で約 1.5 コア）。原因は未特定（パイプへの書き込みと共有メモリの読み取りではないことは確認済み）
3. **色**：取り込んだ映像の暗部が、元の動画より 5 段階ほど暗い（白は一致）
4. **mac のミュート**：録画が始まるまでの準備中は音が出る（タップは録画開始時に作るため）。Windows はジョブ開始時からミュートする
5. **画面共有・Mission Control**：録画中に画面共有で接続していたり、Mission Control を開いたりすると、取り込みが止まったりコマが乱れたりする
6. **ページを同時録画のコマの乱れ**：一定時刻ごとに最新のコマを書く方式のため、動画の fps と同じだと欠けと重複の組が出る（Windows と同じ方式）
7. **未実施の試験**：2時間・6本の受け入れ試験、4ページ・30分、60分の連続運転（S5）、ロックとスリープ（S7）、macOS 15、自己署名でのアップデート（S8）
